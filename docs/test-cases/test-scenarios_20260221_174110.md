# Test Scenarios Specification

> ⚠️ **Scope: Reduced Coverage per Specification**
>
> The following aspects are **excluded from test scope** per specification section "Excluded from Test Scope":
> - **Format validation** (email regex, phone E.164 detailed patterns, full_name special character combinations): Delegated to Middleware (Zod/Pydantic). Only field presence validation tested (missing → 400).
> - **Uniqueness race conditions** (parallel requests with same email/phone): Handled by DB unique index. Only sequential conflict (409) tested.
> - **PII Logic combinations** (name/email token validation in password): Covered by unit tests of shared library. Only basic happy/sad path at API level.
> - **SMS Delivery Guarantee** (user actually receiving OTP): Owned by Notification Service. Only queue submission success (201) and gateway unavailability (503) tested.
> - **Boundary value lengths** (e.g., 101 characters in full_name, 65 characters in password): Delegated to DB schema validation.

## Security Notes

### Password Validation (PII Protection)
- **Substring Matching:** Case-insensitive. Full name is tokenized by delimiters: `.`, space, `-`. Email is tokenized by extracting part before `@`.
- **Example:** If `full_name="John A. Smith"` → tokens = ["john", "a", "smith"]. If `email="john.smith@example.com"` → tokens = ["john", "smith"]. Password `John1@Smith` violates both rules.
- **Scope:** Tested via REG-NEG-PWD-05 (full name token) and REG-NEG-PWD-06 (email token) at API level. Comprehensive token generation logic covered by unit tests of shared library.

### JWT Token Security
- **Claims Validation:** All POS scenarios verify token structure: `exp` (Unix timestamp, +15 min), `sub="registration"`, `email` (user email), `aud="sms-verification"`. Password and phone MUST NOT be in token.
- **Algorithm:** HS256 (HMAC-SHA256). Secret key managed by application configuration.

### Data Sensitivity
- **Logging Restriction:** Per specification, plaintext logging of password, full email, full phone is forbidden. Tested implicitly via compliance with spec (no explicit log validation at API level; coverage in application security audit).

### External Dependency: SMS Gateway
- **Mock Contracts:**
  - **Success:** `{"status": "queued", "message_id": "{UUID}"}` → 201 Created proceeds
  - **Failure (503):** Gateway returns 503 or timeout → 503 Service Unavailable, transaction rolled back
- **Scope:** Only queue submission and gateway unavailability. Actual SMS delivery and OTP validity tested in Notification Service and verification endpoint (`POST /api/v1/users/verify`).

## Test Execution Order & Cleanup Strategy

1. **POS scenarios (REG-POS-01, REG-POS-02):** Run first. Each creates a unique user. **Cleanup immediately after each scenario** (DELETE /users/{UUID}) to avoid email/phone conflicts in subsequent tests.
2. **IDEM scenarios (REG-IDEM-01 through REG-IDEM-03):** Run as a sequence. REG-IDEM-02 depends on REG-IDEM-01 creating a record within 5-min cache window. REG-IDEM-03 requires clock manipulation (>5 min delay) or test data pre-setup.
3. **NEG scenarios requiring unique emails (REG-NEG-*):** Each uses fresh `{UNIQUE_EMAIL}` to avoid transient 409 conflicts during validation testing.
4. **Conflict scenarios (REG-NEG-CONFLICT-01, REG-NEG-CONFLICT-02):** Require pre-populated records:
   - `{EXISTING_EMAIL}`: Create via successful POS → store → use in REG-NEG-CONFLICT-01 → cleanup after
   - `{EXISTING_PHONE}`: Create via successful POS → store → use in REG-NEG-CONFLICT-02 → cleanup after
5. **L10N scenarios (REG-L10N-01 through REG-L10N-05):** Each creates a unique user. Cleanup immediately.
6. **Service failure scenario (REG-NEG-SERVICE-01):** Mock SMS Gateway to return 503. Verify DB rollback (no record created). Cleanup: N/A.
